**The 2026-08-15 "this session ended in a real failure" entry below is superseded — the Jekyll restructuring was never actually broken.** This was verified by a separate Claude Code session (working with Sarah directly on a different project, sarah-strategic, which shares this site's design lineage) while this project's own session was idle, specifically to resolve the open question left at the end of 2026-08-15: what did "it didn't work" actually mean.

Result: clean build in under half a second, all 8 pages generated in `_site/` (`index.html`, `about.html`, `etc.html`, `work/index.html`, plus `work/kidhq.html`, `work/see-lexus.html`, `work/travis-county.html`, `work/wdywk.html` — matching the existing live URLs exactly), output inspected directly and grepped for any leftover `{% %}` / `{{ }}` syntax — none found. The `site.case_studies` loop on `work/index.html` resolved correctly into real case-study tiles.

**Root cause of "it didn't work," now confirmed:** Sarah was viewing the site via VSCode's built-in Live Preview extension at `http://127.0.0.1:3000/...?vscode-livepreview=true` — a plain static file server pointed directly at the raw source files. Those files still contain unprocessed YAML front matter and Liquid tags (`--- layout: default ... ---`, `{% for study in site.case_studies %}`, `{{ study.title }}`), which a static server has no ability to interpret — it served their literal text content as the page body, which is exactly what appeared in her screenshot. This is not a Jekyll defect and not something the 2026-08-15 session could have prevented by building differently; it's a mismatch between the preview tool and the file type. The 2026-08-15 session's response to her — "that's just what happens with Jekyll" — was not wrong, but it stopped short of identifying *why* (wrong server for the file) or offering the fix, which is almost certainly why the session ended rather than continuing.

**The fix, going forward, for local preview of this site:** use `bundle exec jekyll serve --livereload` and view the URL it prints (typically `http://127.0.0.1:4000`) — that runs the real Jekyll build and auto-refreshes on save. Do not point VSCode Live Preview, or any other static file server, at the project root while `_layouts`/`_includes`/`_case_studies`/front-matter files are present — it will always show raw template source, regardless of whether the Jekyll conversion itself is correct.

**Status of the uncommitted Jekyll work as of this entry:** still uncommitted, exactly as left on 2026-08-15, now confirmed sound. Committing it (in reviewable chunks) is the planned next step, pending Sarah's sign-off — see `BACKLOG.md`.

Then a full page-by-page QA pass — she batched tickets across every page, then worked through review rounds against the rendered result. Two structural mistakes are worth banking as lessons since they cost several correction rounds each:

**Lesson: unreset browser-default margins on semantic elements (`blockquote`, `figure`).** Spent 3–4 rounds chasing a "testimonial cards aren't left-aligned" bug by patching the *parent* containers (`display: contents` removal, explicit widths, flex properties) — the real cause was that `.testimonial` is applied to a `<blockquote>`, and blockquotes get a browser-default `margin: 1em 40px` that was never reset. Same bug, same fix, hit again immediately after on `.case-figure` (a `<figure>`, same default-margin behavior) when she said the images weren't spanning full width. Fixed both at the root — added `blockquote, figure { margin: 0; }` to the shared reset — instead of patching each component individually. Takeaway for next time: when a layout bug survives multiple "should be right" CSS reads, check the *element's own tag defaults* before re-auditing ancestors again.

**Lesson: don't build wrapper-avoidant structure when the mockup's rhythm depends on grouping.** Repeatedly guessed at case-study "Concept → Launch" spacing (24/48px, then 32/64px) by putting flat margin values on sibling `<p class="case-note">` + `<figure>` elements, reasoning no wrapper was needed. Wrong four times running — she'd asked from round one whether it should be "its own container" and the answer was yes. Rebuilt as `.case-pair` — one wrapper div per note+figure(or video/dark-quotes), one spacing rule on the wrapper — and the "terrible spacing" complaint stopped. The generalizable mistake: when the same numeric tweak gets corrected twice, the fix usually isn't a better number, it's a missing structural container.

Also mis-scoped a "fix" for Awards/case-study "muted" text: swapped `--color-muted` (a gray `color-mix`) for `--olive-text` everywhere it was used, as a broad recommendation she approved — but it turned out wrong in 3 of 4 spots once she saw it rendered (`.work-tile__hook`, `.case-note`, `.award__meta` all needed to go back to ink; only the case-study quote-band citation was actually supposed to stay olive).
